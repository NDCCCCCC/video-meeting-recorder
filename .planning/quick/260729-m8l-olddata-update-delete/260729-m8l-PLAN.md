# Quick Task 260729-m8l: OldData 捕获 — update/delete 差异对比

## 1. 一句话结论

引入 `audit.RecordChange(ctx, opts)` 服务层 helper，在 6 个代表性 update/delete 操作点（用户 CRUD + 角色 CRUD + 权限分配）抓取 before-state 并通过现有 Sanitizer 管道落审计表；剩余 ~50 个 update/delete 操作的接入模式以"清单 + 代码模板"形式记录在 SUMMARY，留作后续任务逐批补齐。

---

## 2. 目标与背景

### 2.1 任务来源（来自 260729-lr4 HANDOFF）

- 上一轮任务把 audit 覆盖率从 14% 提到 100%（63 个写路由），并接入了 Sanitizer 阻断凭据原文入审计表
- 已知缺口：**audit middleware 只能抓到 NewData**（即请求体），对 update/delete 类操作无法拿到"被改之前是什么"
- OldData 字段在 `AuditLog` 模型中已存在且已建索引（`internal/models/audit_log.go:31`），但**全仓仅 0 处填充**

### 2.2 设计取舍（4 个候选方案对比）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| GORM callbacks (BeforeUpdate/BeforeDelete) | 透明、零侵入 | 每次 DB 写都触发（含内部维护写），需要过滤噪声；ctx 难以贯穿 | **拒绝** — 性能与噪声问题难解决 |
| **Service-layer snapshot → RecordChange** | 显式可控，6 处即可证明模式可行，Sanitizer 自动复用 | 需要每处补 3-5 行代码 | **采纳** |
| Wrap every handler（pre-query middleware） | 中间件统一 | 中间件不知 handler 会改哪个 model，要预解析路径；批量操作不可用 | 拒绝 — 中间件盲改 |
| GORM plugin（按 model 类型） | 透明 + 可限定范围 | 侵入 schema 层，需重新注册 plugin；service 调用栈深处 ctx 易丢 | 拒绝 — 改动面 ≥ 方案 2，但维护成本更高 |

**采纳方案 2** 的核心理由：service 层有完整的 `*gorm.DB` + 业务方法参数（`currentUserID`），可以在 mutate 之前 `s.db.First(...)` 拿到 OldData；不依赖任何反射/ctx 透传魔术；Sanitizer 已经在 `LogOperation` 内部调用，自动覆盖 OldData。

## 3. 任务列表

### Task 1（auto）：新增 `RecordChange` helper + 接入 6 个代表性站点

**预期产出**：

1. `internal/services/audit/audit_log_service.go` 新增方法：

   ```go
   type RecordChangeOpts struct {
       Action     string                 // 操作类型
       Module     string                 // 模块
       Resource   string                 // 资源描述（如 "user:42"）
       ResourceID *uint                  // 资源主键
       OldData    interface{}            // 变更前快照（可以是 map/struct/任意）
       NewData    interface{}            // 变更后状态
   }

   // RecordChange 服务层记录变更（包含 OldData），自动复用 Sanitizer。
   // 适用于 service 层已经掌握 OldData 的场景（snapshot-then-mutate 模式）。
   // 中间件层路径仍走 AuditOperation（middleware 自动捕获请求体为 NewData）。
   func (s *AuditLogService) RecordChange(ctx context.Context, opts RecordChangeOpts) error {
       req := &LogOperationRequest{
           Action:     opts.Action,
           Module:     opts.Module,
           Resource:   opts.Resource,
           ResourceID: opts.ResourceID,
           OldData:    opts.OldData,
           NewData:    opts.NewData,
           Status:     models.StatusSuccess,
       }
       return s.LogOperation(ctx, req)
   }
   ```

   复用现有 `LogOperation` → `s.sanitizer.Sanitize(oldData)` → `generateDiff` → 异步队列 管道，零新增字段。

2. **6 个接入点**（按风险递减排序）：

   | # | 文件:方法 | 模式 |
   |---|---|---|
   | 1 | `user_service.go:UpdateUser` | First(&user) 已有 → snapshot {id, full_name, email, is_active, allowed_ips, role_ids} → mutate → RecordChange(ModuleUser, ActionUpdate) |
   | 2 | `user_service.go:DeleteUser` | First(&user) → snapshot → s.db.Delete → RecordChange(ModuleUser, ActionDelete) |
   | 3 | `user_service.go:ResetPassword` | First(&user) → snapshot（email/username 即可，不要记密码哈希） → mutate → RecordChange(ModuleUser, "reset_password") |
   | 4 | `role_service.go:UpdateRole` | First(&role) → snapshot → mutate → RecordChange(ModuleRole, ActionUpdate) |
   | 5 | `role_service.go:DeleteRole` | First(&role) → snapshot → delete → RecordChange(ModuleRole, ActionDelete) |
   | 6 | `role_service.go:AssignPermissions` | First 旧权限列表 → 写入新权限 → RecordChange(ModuleRole, "assign_permissions", old, new) |

3. **模板（用户 update 为例）**：

   ```go
   // UpdateUser 更新用户
   func (s *UserService) UpdateUser(...) (*models.User, error) {
       var user models.User
       if err := s.db.First(&user, id).Error; err != nil {
           return nil, errors.New("用户不存在")
       }

       // ★ Snapshot OldData BEFORE mutation
       oldSnapshot := map[string]interface{}{
           "id":          user.ID,
           "username":    user.Username,
           "email":       user.Email,
           "full_name":   user.FullName,
           "is_active":   user.IsActive,
           "allowed_ips": user.GetAllowedIPs(),
           "role_ids":    user.GetRoleIDs(),
       }

       // ... 现有 mutate 逻辑 ...

       // ★ 记录变更
       resourceID := user.ID
       s.auditService.RecordChange(ctx, audit.RecordChangeOpts{
           Action:     models.ActionUpdate,
           Module:     models.ModuleUser,
           Resource:   fmt.Sprintf("user:%d", user.ID),
           ResourceID: &resourceID,
           OldData:    oldSnapshot,
           NewData:    newSnapshot, // mutate 后的 map
       })
   }
   ```

   **ctx 来源**：service 层现有方法大多接收 `currentUserID uint` 参数（隐含的 ctx）。需要把 `ctx context.Context` 加入方法签名？检查现有签名：
   - `UpdateUser(id uint, req *UpdateUserRequest, currentUserID uint)` — **没有 ctx**
   - `DeleteUser(id uint, currentUserID uint)` — **没有 ctx**

   **决策**：本次不修改 service 方法签名（避免大范围改动），而是要求 handler 层在调用 service 时**自行**调一次 `s.auditService.RecordChange(c.Request.Context(), opts)`。即：handler 在 `c *gin.Context` 中既有 ctx 又有 currentUserID，做 service 调用 → 拿到 OldData/NewData → handler 内部 RecordChange。

   这与中间件路径正交：中间件记录"请求级"审计（含 HTTP 上下文），service/handler RecordChange 记录"业务级"OldData。两条路径的 LogOperation 写入不同 audit_logs 行（同一请求两条记录）。

   **最终调用模式**（用户 update 为例的 handler）：

   ```go
   func (h *UserHandler) UpdateUser(c *gin.Context) {
       // ... 解析参数 ...
       oldUser, newUser, err := h.userService.UpdateUserReturningOldAndNew(...) // 见下文

       resourceID := newUser.ID
       h.auditService.RecordChange(c.Request.Context(), audit.RecordChangeOpts{
           Action:     models.ActionUpdate,
           Module:     models.ModuleUser,
           Resource:   fmt.Sprintf("user:%d", newUser.ID),
           ResourceID: &resourceID,
           OldData:    oldUser.ToMap(),
           NewData:    newUser.ToMap(),
       })
   }
   ```

   **service 改造**：`UpdateUser` 返回 `(*models.User /* old */, *models.User /* new */, error)` — 增加一个返回值，把 mutate 前的 user 作为 old 返回；handler 负责转 map 并 RecordChange。

   **对未在中间件层的 service 调用**（如 `RoleService.AssignPermissions` 由 `role_handler` 调用）：handler 拿到 service 返回值后 RecordChange 即可。

4. **ctx propagation 完整性检查**：6 个接入点的 handler 当前是否全部用 `c.Request.Context()` 调用 service？grep `c.Request.Context()` 应当 > 0。如果有 service 方法直接走 `context.Background()`，需先修复（参考 task 260729-lr4 已做的"ctx 穿透"）。

5. **Sanitizer 自动覆盖**：`RecordChange` → `LogOperation` → `s.sanitizer.Sanitize(oldData)` → `s.sanitizer.Sanitize(newData)`。**password / password_hash / secret / token 类字段会被自动 redact**，即使 OldData 里有密码哈希也不会泄漏。但 ResetPassword 的 OldData snapshot 必须**显式排除 `PasswordHash` 字段**（即便 sanitizer 会过滤，预先不 snapshot 是更干净的实践）。
