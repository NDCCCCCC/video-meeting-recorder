# 前端偶发 401（token 刷新竞态）修复

## 根因诊断（代码证据）

用户日志特征：同一秒一批并发 401（/files/stats、/recordings、/input-configs/active、/transcriptions/active）→ 之后数分钟内每次页面跳转继续 401 → 最后手动刷新页面才恢复。后端 token 校验是无状态的（`internal/middleware/auth.go:96` 仅 `ValidateToken` SM4 解密 + claims 校验，不查 session 表），因此"持续 401"必然来自前端持续携带过期/无效 token，而非服务端会话状态。

| # | 根因 | 证据 |
|---|------|------|
| RCA-1（主） | **refresh 单飞窗口过窄**：`refreshingPromise` 在 leader 自己完成 retry 后立即置 null，其后才到达 401 的请求各自再成为 leader 重新 refresh，每次 refresh 都轮换 RT 并让服务端在宽限期后停用旧 RT session | `frontend/src/api/apiClient.ts:209`（赋值）、`:237-240`（finally 置 null）；后端 `internal/auth/sm4_token.go:407-425`（5s 后停用旧 session） |
| RCA-2（主，与日志吻合） | **retry 仍 401 时无二次恢复**：refresh 成功后用新 token 重放若仍 401，直接 `throw new Error(data.message || ...)`，不刷新、不登出、不清 store，页面停留无数据——错误 message 即后端原文（如"未授权：缺少认证令牌"），与用户日志 `Failed to load stats: Error: 未授权` 完全一致 | `frontend/src/api/apiClient.ts:194-197`（follower 分支）、`:222-225`（leader 分支）；后端 401 原文 `internal/middleware/auth.go:87-90` |
| RCA-3 | **冷却期误登出**：refresh 一旦失败一次，5s 冷却期内所有 401 直接 `handleUnauthorized()`（清 token + 跳登录），瞬时网络抖动即整体登出 | `frontend/src/api/apiClient.ts:14-16`（REFRESH_COOLDOWN=5000）、`:178-182` |
| RCA-4 | **无主动刷新**：后端 login/refresh 响应均返回 `expires_in`（`internal/auth/service.go:76,84`；AT 默认 2h，`internal/config/config.go:515-516`），前端两处调用点完全丢弃该值，只能被动等 401 | `frontend/src/api/auth.ts:57`、`frontend/src/api/apiClient.ts:114-117` |
| RCA-5 | **良性并发刷新被后端判为重放攻击并撤销全会话**：`GracePeriod = 5s`（`internal/auth/sm4_token.go:34`）+ tokenCache 每 TTL 过期（`:296-309`）；超窗再用旧 RT → `RevokeUserSessions` 撤销该用户全部会话（`:363-371`）。多标签页 / 迟到 401 的二次刷新一旦与 5s 窗口错开即触发 | `internal/auth/sm4_token.go:34,296-309,363-371,407-425` |
| RCA-6 | **内存/localStorage 分叉（隐患）**：`saveToken` 直改 localStorage 的 auth-storage JSON，zustand in-memory 不更新（当前无运行期 `set()` 调用点，故为隐患而非本次直接诱因） | `frontend/src/api/apiClient.ts:57-85` vs `frontend/src/stores/authStore.ts:19-99` |
| RCA-7 | **绕过 apiRequest 的裸 fetch 无 401 恢复** | `frontend/src/api/audit.ts:43-47`（localStorage 直读）、`frontend/src/api/system.ts:47-55`、`frontend/src/api/video-file.ts:56,229,256` |

**修复策略**：Task 1 建立"单飞 refresh + recent-token 缓存重放 + retry 再刷新 + 主动刷新"的统一 token 状态机（根治 RCA-1/2/3/4）；Task 2 收口全部裸 fetch 并消除内存/存储分叉（RCA-6/7）；Task 3 放宽后端宽限窗口并补首个回归测试（RCA-5）。
